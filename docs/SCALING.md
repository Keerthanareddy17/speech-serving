## a. Training memory

**Training state costs 16 bytes per parameter, so an unsharded 4.8B model needs 76.8 GB before a single activation, which cannot fit on one 80 GB GPU; 800M (24.1 GB with checkpointing) can.**

In plain words: each parameter is stored several times. Training keeps a bf16 copy to compute with, a bf16 gradient, and, because Adam needs high precision, an fp32 master copy plus two fp32 running averages (m and v). 2 + 2 + 4 + 4 + 4 = **16 bytes/param** **[assumed: standard mixed-precision Adam accounting]**.

Activation assumptions **[assumed]**: sequence length 4096, micro-batch 2 (8,192 tokens per GPU per step), bf16, flash attention (no s×s score matrix).

```
state            = 16 * N_params
activations      = L * 34 * s * b * d  +  logits            (no checkpointing)
activations_ckpt = L * 2 * s * b * d  +  34 * s * b * d  +  logits
logits           = s * b * V * 8 bytes   (fp32 logits + fp32 gradient)
```
Without checkpointing every layer keeps all its intermediate tensors for the backward pass. With checkpointing each layer keeps only its input and recomputes the rest during backward, one layer at a time, so memory drops a lot but you pay one extra forward pass (33% more compute). The logits term is large because the vocabulary is 156,940 (audio tokens); a fused or chunked loss would shrink it.

## b. How it splits across GPUs

**For 4.8B on 80 GB GPUs (usable 72 GB), everything fits with activation checkpointing except DDP, 16 GPUs; HSDP sends 1.2 GB per GPU across nodes per step versus 27.0 GB for 16-way FSDP (22× less).**

In plain words:
- **DDP** copies the whole model on every GPU and only averages gradients. Simple, but memory per GPU never shrinks.
- **FSDP** splits (shards) the 16 bytes/param across GPUs. Each layer is all-gathered just before use and freed after, and gradients are reduce-scattered. Memory per GPU = 16N / GPUs + a small gathered working set.
- **HSDP** shards only inside one 8-GPU node (fast NVLink) and keeps a full replica per node. Across nodes only the small gradient shard is averaged.
- **TP** (tensor parallel) splits each matrix multiply across 2 or 4 GPUs in a node; it cuts weights and activations per GPU but needs an all-reduce inside every layer, so it stays within a node.

Per-GPU communication volume, per micro-batch step (accumulation 1), ring collectives, N = parameters, D = group size:

```
DDP   : 2 * (D-1)/D * 2N                       (all-reduce of bf16 grads)
FSDP  : 3 * (D-1)/D * 2N / tp                  (all-gather fwd, all-gather bwd, reduce-scatter)
HSDP  : 3 * (7/8) * 2N  [in node]  +  2 * (R-1)/R * 2N/8  [across nodes, R = node replicas]
TP    : L * 4 * 2 * (tp-1)/tp * (s*b*d*2)      (in node; checkpointing adds another forward's worth, not modelled)
```
Why HSDP cuts cross-node traffic: with FSDP over 16 GPUs the three full-model collectives run in one ring that crosses the node boundary, so all of that volume rides the slow inter-node link. With HSDP the full-model collectives stay inside the node on NVLink, and the only cross-node message is one all-reduce of the gradient *shard* (1/8 of the gradients). A flat group bigger than a node is treated as inter-node bound **[assumed simplification: real NCCL uses hierarchical algorithms and does better]**.

Bandwidths **[assumed]**: intra-node 450 GB/s per GPU, inter-node 50 GB/s per GPU. Compute time = 6·N·tokens / (peak 989 TFLOPs × MFU 0.4). Comm time = intra/NVLink + inter/network, summed (an upper bound: real runs overlap comm with compute).

## c. Data and training compute

**2,000,000 hours of audio is 5.95e+11 SNAC tokens; one epoch costs about 2,005 GPU-hours for 800M and 12,032 GPU-hours for 4.8B at an assumed 40% MFU.**

Tokens = hours × tokens per audio hour = 2,000,000 × 297,483 **[measured: results/pipeline.json, 33,113 clips; the pure codec rate would be 7 × 24000/2048 × 3600 = 295,312; the measured rate adds the rounding-up of each clip's last frame]**. It counts audio tokens only, not the text prompt tokens.

```
training FLOPs = 6 * N * D          (N = parameters, D = tokens)
GPU-hours      = FLOPs / (peak FLOPs/s * MFU) / 3600
```
In plain words: every token passes through every parameter once forward (2 FLOPs per parameter: one multiply, one add) and the backward pass costs twice that, hence 6. MFU says what fraction of the GPU's peak we really achieve: 989 TFLOPs × 0.4 = 396 TFLOPs effective **[assumed]**.

| 800M | 2.86e+21 | 2,005 | 2,674 | 0.3 | 0.1 |
| 4.8B | 1.71e+22 | 12,032 | 16,042 | 2.0 | 0.5 |
| Orpheus 3B (reference) | 1.18e+22 | 8,274 | 11,031 | 1.3 | 0.3 |

Days assume perfect linear scaling and one epoch, so they are lower bounds. 6ND ignores attention FLOPs, which are small at this sequence length.

## d. Data pipeline at that scale

**Tokenizing 2,000,000 hours takes about 4,990 L4-hours at our measured 6.68 audio hours per minute, and it is bound by the GPU (SNAC encode), not the CPU, which has about 10× headroom.**

```
L4-hours = hours of audio / (audio-hours per minute * 60)
```

## e. Serving

**At our measured 6 realtime streams per L4 you need 17 GPUs for 100 concurrent streams and 167 for 1,000; planning with a safety margin (5 per GPU, the next lower level that passed) gives 20 and 200.**

```
GPUs = ceil(concurrent streams / streams per GPU)
```
Measured **[results/step6c_final_sweep.json]**: max 6 streams where p95 RTF < 1.0 with no gaps (RTF p95 0.996, TTFA p50 187 ms / p95 214 ms at 6 streams; TTFA p50 137 ms at 1 stream). Level 7 already fails. At 6 streams the margin is thin (RTF p95 so close to 1.0), hence the conservative figures. **[assumed]** for the GPU counts: every stream is continuously generating, load is spread perfectly across GPUs, and one websocket stays on one GPU (no cross-GPU communication). Real traffic has idle time and bursts; this is peak-concurrency sizing, not a traffic forecast.

Where the limit comes from **[measured, DECISIONS step 6b]**: a realtime stream needs 82.03 tokens/s, a budget of 12.2 ms/token. Alone, single-stream decode takes 8.11 ms/token (123.3 tok/s, step 1d). In the server at 6 streams vLLM takes 11.73 ms/token, because vLLM and SNAC run in two processes and the GPU time-slices between them.

What would raise per-GPU capacity:
- **One-process serving or MPS** (stop the time-slicing). In our step 6a benchmark vLLM *alone* stayed within the 12.2 ms budget up to batch 16 measured, and about 27 by linear interpolation. That would be 4 / 38 GPUs for 100 / 1,000 streams. **This is an upper bound, not a result:** SNAC also needs GPU time and we could not run either fix here (vLLM 0.32's AsyncLLM cannot run in-process; MPS failed in our container).
- **Bigger GPUs.** Decode is mostly memory-bandwidth bound. An H100's bandwidth (3350 GB/s **[assumed spec]**) is 11× an L4's (300 GB/s **[assumed spec]**), so per-GPU capacity would rise, but we have not measured it, and cost per stream is a separate question.
- Reducing SNAC's share of GPU time did not help in our tests (step 6b), so more SNAC micro-optimisation is not the lever.
